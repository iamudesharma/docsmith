Concurrent 20-PDF validation (`scripts/concurrency_report.py`, 21 October): 20 synthetic PDFs / 316 pages (the 10 base fixtures plus 10 `pdfunite` compositions), all uploaded at once and run three times per service configuration. With the default `workers=2`/`pdf_workers=4`, the median makespan was 22.5 s (range 20.9–23.4); with `workers=6`/`pdf_workers=2` it was 17.1 s (16.9–17.1), p95 job latency 13.4 s → 9.3 s and peak sampled process-tree RSS 104 → 158 MB. All 20 documents passed every check in all six runs: 20/20 page counts, 311/311 exact page texts, 71/71 content markers, 30/30 PDF table cells, OCR CER 0.0000 over six scan cases, 7/7 exact invoice-occurrence counts (hidden OCR not duplicated), 1/1 retained diagram source and 1/1 clean corrupt-PDF failure. Results were byte-identical across configurations once job ids and elapsed time were excluded. The host was under background load (~4–7 load average, ~3 GB swap in use), so absolute times are conservative; see CONCURRENCY.md / concurrency-results.json.

Hindi + English OCR stress fixture (`scripts/ocr_accuracy.py`, 22 October): a committed three-page raster-only PDF (`fixtures/hindi-english-complex.pdf`) with dense Devanagari/Latin text, a marks table, stamps, barcodes, subtle noise and a 90°-rotated third page, compared against `fixtures/hindi-english-complex.ground-truth.txt`. With `languages: eng+hin`, 150 DPI rendering and automatic rotation: 3/3 pages, 0 unit errors, 1,007/1,047 Devanagari characters, 1,195/1,180 Latin characters, **3.94% CER**, **19.50% WER**, 29/32 critical fields; page 2 (paragraphs/bullets) reached 0.27% CER. The weak area is scanned tables: page 1's small grid text produced 9.93% CER, 8/12 expected table tokens, and no structured `Table` block because OCR output is line-grouped, not geometric table inference. Page 3 recovered after 90° rotation. Full method and per-field results: `docs/hindi-english-ocr.md` / `docs/hindi-english-ocr.json`.

Commit 6d905f4 and `docs/PIPELINE.md` were reviewed against the code (findings with file references: `docs/CODE-REVIEW.md`); the confirmed gaps were implemented in four phases. Phase 1: resume artifacts carry a `checkpoint_format` version, checkpoint/progress snapshots are complete and page-ordered and refresh live in both sequential and parallel modes (a 500-page parallel job reported progress 0→101→232→364→487→500 instead of 0 throughout), completed units survive a batch-worker error instead of being discarded, `result.json` is assembled by streaming the unit files, stale temp files are swept at start, and per-stage timings land in `timings.json`. Phase 2: delimited inputs above `limits.stream_bytes` (16 MiB default) release each chunk's blocks once its unit file is written, and `result.md`/`result.txt` stream the unit files. Phase 3: the OCR budget is machine-wide across worker processes via `flock` slot files under the service data dir, on top of the in-process semaphore. Phase 4: batch scheduling is dynamic (atomic work queue), a page's render/OCR failure no longer aborts the document, Poppler page-count mismatches fall back to per-page text extraction instead of shifting text, and sparse-text image-free pages (<24 native chars) are rendered for OCR with duplicate suppression (test `sparse_text_pages_render_for_ocr_without_duplicating_native_text`).

Cross-platform check: the `benchmark-linux` workflow (GitHub Actions ubuntu-latest, run 38333778237; quick shapes) completed the same harness with a portable host probe and its own quick/shape counts: 500k-row streamed CSV 7.4 s wall, **120 MB sampled peak process-tree RSS**, 254 MB result (compact: 3.5 s, 95 MB RSS, 85.7 MB result); 24 scanned pages with OCR 17.0 s; 400-page digital PDF 0.8 s; crash recovery resumed in 0.7 s; cancellation reaped all descendants. Unlike macOS, Linux RSS tracks the streamed design's real bound. Shared-runner timings are smoke signals, not target-hardware evidence.

Large inputs were re-measured twice on 13 October 2026 (see perf-large-inputs.json for the latest run): a 2000-page digital PDF completes in 13–16 s release (four batch workers; 2000 units; result writes 0.06–0.08 s), 80 scanned pages with OCR take 47–81 s (OCR is >90 % of the critical path), a 100-page mixed PDF 24–38 s, and a 30-page image-heavy PDF with 90 panels 38–67 s; OCR-bound runs vary strongly with host load (the machine was at load ~3.2 with 1.7 GB swap in use for the slower run). A 2M-row/87 MB CSV completes in 13–20 s producing a 1.02 GB result (345.6 MB with `compact_tables`), with stage timings showing 2.5–5.6 s unit writes, 0.4–6.7 s result assembly and 6.9–9.2 s derived-file writes. Streamed tables keep live heap near one chunk: 107 MB peak and 0 MB final versus 915 MB peak and 496 MB final buffered for the same 700k-row CSV, measured with a counting allocator; macOS RSS overstates both because the system allocator keeps freed pages resident. Crash recovery: with 503/2000 pages complete, the service and worker were SIGKILLed and a restarted service resumed the same job to completion in 11.5 s. Cancellation of a running OCR job left no descendant processes and no temporary files. These remain synthetic inputs; scanned/mixed real corpora are still the practical constraint.
